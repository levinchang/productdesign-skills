# 产品文档结构规范（标准参考）

本文件为**与编辑器无关**的产品与研发文档结构标准，可直接复制到任意项目中使用（任意 IDE、协作平台、非 Cursor 环境均适用）。建立 FeatureList↔PRD↔ER↔时序图↔技术文档↔原型的追溯链，统一 PRD 推荐章节结构与索引表约定。

**使用方式**：将本文件或所在目录 `product-doc-standard/` 复制到项目文档根或 `docs/` 下，按需调整路径与命名后执行即可。在 Cursor 中若启用 product-featurelist / product-prd，会优先读取项目内本标准文档。

---

## 1. 文档根与两区划分

- **文档根目录**：由项目自定（仓库根、`docs/`、`designdocx/`、`product/` 等）。以下称「文档根」。
- **两区**：建议在文档根下区分「设计资产」与「PRD」：
  - **设计资产**：Feature List、ER 图、时序图、技术设计总览、技术文档目录（tech/）等，与 PRD 同级便于引用。
  - **PRD 区**：所有 PRD 按模块或按产品线/端组织；具体目录名与层级由项目约定。

**示例（仅作参考，非强制）**：

```
<文档根>/
├── README.md                     # 总览、文档类型与 PRD 关系表
├── <FeatureList 文件>.md         # 功能清单，命名由项目定
├── <ER 图>.mmd / <ER 说明>.md    # 数据模型，命名由项目定
├── 时序图01_<流程名>.mmd         # 时序图，命名由项目定
├── TECH_DESIGN_OVERVIEW.md       # 可选
├── tech/                         # 可选，技术设计文档
│   ├── README.md
│   └── 01_xxx.md, 02_xxx.md ...
└── 03_prd/                       # PRD 根目录；常见为 03_prd（文档根为 docs/ 时即 docs/03_prd/），可由项目改为 prd、backend、frontend 等
    ├── README.md                 # PRD 撰写规范、目录约定、索引表（见下）
    ├── prototype/                 # 可选，原型可放在 PRD 根下或各子域下
    │   ├── README.md
    │   └── *.html
    └── <模块目录>/                # 如 M1_登录、F1_账户、module_a 等，由项目定
        └── <功能>_PRD.md
```

**通用约定**：Feature List、ER、时序图、技术文档与 PRD 根同级或处于文档根下明确位置；模块目录与文件命名、编号体系由项目统一约定，并在 README 索引表中体现。

---

## 2. 文档追溯链

| 文档类型 | 约定 | 与 PRD 关系 |
|----------|------|-------------|
| Feature List | 文档根下，文件名由项目定 | 每篇 PRD **开头**必须注明「对应 FeatureList 编号」 |
| ER 图 | 文档根下，文件名由项目定 | PRD 中字段键名、校验与 ER 实体一致；技术文档与 ER 对齐 |
| 时序图 | 文档根下，编号+流程名 | PRD 中流程逻辑可引用对应时序图编号 |
| 技术文档(tech/) | 文档根下 tech/ 或等价目录 | 开发实现依据；与 PRD、ER 一致 |
| PRD | 按模块/产品线分目录 | 通过「PRD 索引表」由 FeatureList 编号反查 PRD 文件路径 |

**PRD 单文档 Header（必填）**：每篇 PRD 正文最前，用表格或列表注明「功能名称」「对应 FeatureList 编号」「对应蓝图场景 ID（SCN-xx）」「对应能力 ID（CAP-xx）」「所属模块」「文档版本」「作者/评审人」「对应 ER 实体」「对应时序图（如有）」。推荐一个 PRD 仅对应**单一** FeatureList 编号；如需覆盖多个需求，应优先在 Feature List 中拆分为多条编号，再为每条编号单独建 PRD 文档。

---

## 3. PRD 目录与命名（项目可定制）

- 按模块或产品线建目录，名称与业务一致；是否区分前后台、用 M/F 等前缀由项目定（如 `F3_校招信息表/`、`ALM_告警管理/`）。
- **默认一条 FeatureList 编号对应一篇 PRD**：推荐以 FeatureList 编号为最小粒度拆分 PRD，避免在同一文档内混写多个编号对应的需求；仅当多个编号共享同一用户目标、同一主入口/页面、同一状态流转闭环，且能由同一批研发/测试在一次迭代中完成并统一验收时，才允许在索引表/README 中明确声明为一小组并合并到同一篇 PRD。
- **文件命名建议**：`<FeatureList 编号>_<功能名称>_PRD.md`，例如：
  - `F3.1_校招页概览与24h统计_PRD.md`
  - `ALM-1.1_告警接入与联动_PRD.md`
- 若历史遗留文档中存在「一文多编号」情况，在后续迭代中应优先调整 Feature List 并拆分为多篇 PRD；新建文档不应再采用「一文多编号」的写法。
- 同目录下如有纯规则说明、逻辑说明等文档，可单独命名为 `<模块>_逻辑说明.md` 等，不作为 PRD 正文。

## 4. PRD 单文档结构（推荐可裁剪章节结构）

若项目已有自己的 PRD 模板，请以项目约定为准；若项目尚未约定，则推荐采用下述「可裁剪章节结构」，在不破坏可读性与追溯性的前提下，可按需合并或省略部分章节：

| 序号 | 章节 | 内容要点 |
|------|------|----------|
| 0 | **Header** | 功能名、FeatureList 编号、对应蓝图场景 ID（SCN-xx）、对应能力 ID（CAP-xx）、所属模块、文档版本、作者/评审人、对应 ER/时序图（如有） |
| 1 | **项目背景与目标** | 为何做、做什么、期望效果；可含用户故事、业务 KPI、范围说明 |
| 2 | **用户与场景概览** | 主要用户角色、典型使用场景与路径，避免后文脱离语境 |
| 3 | **范围与版本（本次/非本次）** | 明确本次版本内/版本外内容，避免范围膨胀和需求复读 |
| 4 | **功能需求（按模块/Story 列表）** | 按模块/Story 拆分 4.x 小节，每个 4.x 建议包含：4.x.1 页面元素与展示规则；4.x.2 交互逻辑与状态流转；4.x.3 字段说明（当涉及新建/编辑/列表且字段复杂或易产生歧义时必须补充）；4.x.4 异常与系统边界 |
| 5 | **流程与交互（含流程/时序/状态图约定）** | 列出关键业务流程与交互闭环，为关键流程补充 Mermaid（默认）或 PlantUML 图表源码；截图按评审或交付需要生成 |
| 6 | **非功能与约束** | 性能、稳定性、安全、合规、可观测性等非功能需求（按需补充） |
| 7 | **验收标准** | 面向测试/业务验收的 AC、关键用例抽象、依赖与待定项、版本里程碑等（推荐补充） |

## 5. 索引表约定（通用）

- **PRD 根目录的 README**：说明与 FeatureList 的对应关系、PRD 单文档结构、目录与命名约定；**必须包含「FeatureList 编号 ↔ 功能简述 ↔ PRD 文件路径」对照表**。若 PRD 按多子域拆分，可在各子域 README 维护各自索引表，或汇总在 PRD 根 README。
- 新增或重命名 PRD 时，必须同步更新对应索引表。
- 可选：在 README 中补充 UI/设计规范、模块与菜单/页面映射。

---

## 6. 原型目录与规范（通用）

- **位置**：由项目约定。常见为 PRD 根下 `prototype/` 或各产品线/端下分别 `prototype/`。
- **技术栈**：HTML + Tailwind CSS（CDN）+ Lucide Icons（或等价）+ 原生 JS，无后端、无构建。
- **每个原型目录必须有 README.md**：与 PRD 对应关系、设计规范摘要、文件说明、使用方式。HTML 关键区块用注释标注 PRD 编号或功能名（如 `<!-- [1.1] 登录弹窗 -->`）。

---

## 7. 根据 PRD 生成或更新原型（可选）

执行时：确认项目约定的文档根、PRD 根、原型目录与 README；读取目标 PRD 及所属 README 中的设计/UI 规范；在约定原型目录下新增或修改 HTML，并更新该目录 README 的「与 PRD 对应关系」和「文件说明」。原型以占位、弹窗、抽屉、页面切换为主，不接真实后端。原型设计应遵循「能还原的尽量还原（应用尽有）」的原则：在不增加后端实现复杂度的前提下，尽可能还原页面布局、组件状态与关键交互流转；如项目已约定 UI/UX 规范（例如 ui-ux-pro-max skill 中的设计原则），应优先遵循该规范。

---

## 8. 技术设计文档（tech/，可选）

文档根下 `tech/` 或项目约定等价目录。tech/README 列出各技术文档及与 ER、时序图、Feature List/PRD 的对应关系；各 .md 按主题拆分，引用 ER、时序图及 PRD，不重复需求描述。可选 TECH_DESIGN_OVERVIEW.md 作总览索引。

---

## 9. 检查清单（创建或修改文档时自检）

- [ ] 新 PRD 在项目约定的模块/产品线目录下，文件名符合命名规范（推荐以 FeatureList 编号为前缀，如 `F3.1_功能名_PRD.md`）。
- [ ] PRD 开头已填 Header（功能名、FeatureList 编号、对应蓝图场景 ID（SCN-xx）、对应能力 ID（CAP-xx）、所属模块、文档版本、作者/评审人、对应 ER/时序图等），且 FeatureList 编号在清单中存在；若一文覆盖多编号，已在 Feature List/索引表中显式声明为一小组并满足强耦合条件。
- [ ] PRD 采用推荐章节结构（或项目自定义模板），至少包含：背景与目标、用户与场景、范围与版本、功能需求、流程与交互、验收标准等关键信息；不存在为了「凑章节」而硬写的空洞内容。
- [ ] 项目约定的 PRD 索引表（README）已更新。
- [ ] 若涉及原型：原型目录 README 中「与 PRD 对应关系」已更新；HTML 关键处已标 PRD 编号或功能名。
- [ ] 字段键名、枚举与 ER 图一致；流程描述引用的时序图编号正确。
