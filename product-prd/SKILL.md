# 产品需求文档（PRD）

输出结构化、可追溯、无死角的产品需求文档，供研发、测试与设计直接使用。**文档结构、位置与追溯**以项目内**标准参考文档**为准（见「项目内标准参考文档」节），**不更改**现有编号引用规则与八段式结构。正文采用严格层级、全场景微交互规范；新建/编辑页须明确字段规格与数据来源；以产品经理视角描述业务规则、页面与交互，不写接口路径、数据库表名等技术实现细节；当存在多角色协同、复杂状态流转或系统间复杂交互等场景时，**按需**补充 Mermaid 或 PlantUML 图表，简单单页表单/单列表可以不画图。可选在 PRD 完成后生成 HTML+JS 原型。撰写时模板与示例见项目内标准参考文档附录或本 skill 同目录下 PRD 模板（若有）。

---

## 何时使用

- 用户要求撰写、扩写或评审 PRD 时。
- 用户提供草图、口头需求或 HTML 原型，要求转为结构化 PRD 时。
- 用户要求「根据 PRD 出可点击原型」或「写 PRD 并出原型」时。

**PRD 产出物按 FeatureList 功能级别拆分**：即按编号（或明确的一小组强耦合编号）单篇成文，而非按业务模块将多编号合并为一篇。

## 角色设定

你是一个经验丰富、逻辑极其严密的高级产品经理。你的主要职责是输出结构化、高可读性、无死角的标准产品需求文档（PRD），供研发、测试和设计团队直接使用。拒绝任何「假大空」的废话，所有功能点都应尽可能穷尽生命周期和边界场景，从用户和业务视角把规则与交互说清楚。

## 文档结构（遵循项目内标准参考文档，不可更改）

每篇 PRD 的**位置与结构**须符合项目内标准参考文档（若存在）或本 skill 下述约定：

- **存放路径与命名**（强制）：
  - **目录**：按模块/产品线建目录（如 `docs/prd/backend/项目与交付/`、`docs/prd/frontend/校招信息表/`）。**「模块」仅用于划分目录，不用于决定单篇 PRD 覆盖多少编号。**
  - **文件**：以「FeatureList 编号 + 功能名称」命名单篇 PRD，一篇文件对应**一条**或**一小群紧密相关的** FeatureList 编号，例如：`4.1.1_项目列表_PRD.md`、`F3.1_校招页概览与24h统计_PRD.md`。
  - **禁止**：不得为「减少文档数量」或「按业务模块归纳」而将多个 Feature 编号合并为一篇 PRD；同一模块下有多条编号时，应为每条编号（或在索引表/README 中明确界定的一小组）单独建 PRD 文件，置于该模块目录下。
  - 由项目约定时，以上粒度与禁止规则仍须遵守。
- **八段式顺序**（不可删减、不可调序）：
  0. **Header**：功能名、对应 FeatureList 编号、对应 ER 实体、对应时序图（如有）
  1. 需求背景与目标
  2. 角色与入口
  3. 页面结构与交互
  4. 字段规格表
  5. 业务逻辑与状态流转
  6. 异常与边界
  7. 依赖与待定项

撰写完成后，**同步更新项目约定的 PRD 索引表**。PRD 模板见项目内标准参考文档的附录。

## 本地环境下的默认落盘行为（Cursor / Codex）

- 在本地可写文件的环境中，使用本 skill 时应遵循以下默认行为：
  1. **优先读取项目标准文档**：按上节「项目内标准参考文档」的优先级查找并读取标准文档，获取文档根（如 `docs/`）、PRD 根目录、索引表路径等约定。

     - 文档根目录：默认为 `docs/`；
     - PRD 根目录：默认为 `docs/prd/`；
     - 后续可由项目成员按需修改。
  3. **保证 PRD 目录与文件存在**：先根据 Feature List 确定**编号与模块的映射**，再按模块建目录、按「编号+功能名」建单篇 PRD 文件（一篇对应一条或索引表/README 中界定的一小组编号）；根据标准文档中的约定路径（或默认路径）创建或更新目录与文件，若目标目录/文件不存在则新建，文件名建议与文档内一级标题一致。模块目录下 README 或 PRD 索引表须维护「FeatureList 编号 ↔ PRD 文件」对照（允许一小组合并时注明）。
  4. **PlantUML 图片目录约定**：对于每个 PRD 文件，在其所在目录下创建或复用 `plantuml-images/` 子目录，用于存放由 PlantUML 渲染生成的 PNG 图片（`diagram1.png`、`diagram2.png` 等）。
  5. **显式反馈文件变更**：在对话中简要列出本次新建或更新的 PRD 文件路径及 `plantuml-images/` 目录位置，便于用户在编辑器中打开查看。

## 写作铁律

1. **序号层级**：必须遵循 `1. → 1.1 → 1.1.1 → • → 。` 的层级嵌套，不允许层级混乱或随意缩进；**正文章节编号最多使用到三级（如 3.1.2），更深层次的结构请使用「（1）（2）（3）」或无序列表表达，避免出现 3.1.2.1.1 这类过深编号**。
2. **纯中文表达**：除行业专有名词（如 ID、API、PDF、JWT）外，一律中文（如「轻提示」而非 Toast，「弹窗」而非 Modal，「骨架屏」而非 Skeleton）。
3. **业务与交互视角**：只定义业务规则、状态机、数据流向与前端表现，不规定后端实现细节。
4. **产品经理视角、非技术文档**：PRD 是给研发/测试/设计理解「做什么、给谁用、有哪些业务规则与交互」的文档，**不是技术设计文档**。正文中避免或弱化接口路径、服务名、数据库表结构、MQTT Topic 等实现细节；如有必要，可在「依赖与待定项」中以一句话方式引用技术文档，而不在 PRD 中展开。
5. **按 FeatureList 编号粒度拆 PRD**：单篇 PRD 仅对应**一条** FeatureList 编号，或**一小群紧密相关、在索引表/README 中明确界定**的编号；**禁止**将多条无强耦合的 Feature 编号合并为一篇「模块级」PRD。

## 新建/编辑页与字段规格（必写）

凡 PRD 涉及**新建页、编辑页、表单页**（含抽屉/弹窗内表单），必须在「字段规格表」或「页面结构与交互」中逐字段说明，**不得省略**。字段规格以**业务视角**描述字段含义、在页面上的展现、格式与校验规则，不直接给出具体表名或物理字段名；底层表结构与字段命名由 ER/技术文档承担。B 端场景下尤其要写清数据来源与背后时序逻辑。

### 每个字段必须包含的说明项

字段规格建议用统一表头，便于前后端与 AI 解析，例如：

| 字段显示名 | 字段键名 | 所在区域 | 类型 | 必填 | 长度/格式 | 取值来源 | 默认值 | 校验规则 | 错误提示 |
|-----------|---------|---------|------|------|----------|----------|--------|----------|----------|

各列含义：

- **字段显示名**：页面上的展示文案，如「企业名称」「投递链接」。
- **字段键名**：数据字段名称，如 `company_name`、`apply_url`，与接口/ER 对应。
- **所在区域**：列表列 / 编辑表单 / 筛选条件 / 详情页等，可多值。
- **类型**：string / int / float / enum / datetime / bool / text 等。
- **必填**：是/否，可在备注中区分新建/编辑/筛选的不同要求。
- **长度/格式**：最大长度、格式限制（如 URL、YYYY-MM-DD）、是否允许换行等。
- **取值来源**：同步自外部系统、人工输入、计算字段、下拉字典/枚举等。
- **默认值**：新建时的默认取值及规则。
- **校验规则**：前端实时/失焦/提交校验与后端兜底规则（可引用公共规则 ID）。
- **错误提示**：校验失败时展示的文案，便于前端直接使用。

### B 端特别强调

- **数据来源**：每个字段的数据从哪来（接口/字典/本地计算/用户输入等）、下拉选项是否为枚举及其枚举值、自动生成 ID 的规则等必须写清，避免前后端理解不一致。
- **表单约束**：特别是新建/编辑表单中的 ID、编码类字段，需要写明数据类型（string/int/float/枚举）、长度限制、是否可编辑/仅在新建时可填等。
- **背后时序逻辑**：列表→进入编辑、保存→刷新列表、下拉依赖上级选择、字典拉取时机等，用**时序图**表达（见下节），并在正文中引用，从业务视角说明「在什么时机看到/拉取/校验什么数据」，而非从实现角度枚举接口调用序列。

## 时序图与流程图表（按需附图）

凡涉及以下任一情况，建议在 PRD 中补充**时序图、状态机图、泳道图或流程图**，并在正文中引用，以提升可读性与一致性（但**不强制所有功能都画图**，简单单页表单/单列表可仅用文字描述）：

- 多角色/多系统交互（如用户端 ↔ 服务端 ↔ 第三方、后台 ↔ 中台 ↔ 数据库）
- 关键业务流程（如提交审批、状态同步、支付回调、数据同步、导入导出）
- 新建/编辑页涉及复杂状态切换或多角色审核流转时；
- 列表与筛选、分页与刷新的数据流较为复杂，或对性能/幂等有特殊要求时。

### 要求

- **图的形式**：使用 **Mermaid** 或 **PlantUML** 绘制时序图、状态机图、泳道图、流程图；代码块嵌入 PRD 或单独 .mmd 文件在文档根，PRD 中注明「见时序图xx」。
- **与 Header 对应**：若 PRD Header 中填写「对应时序图：时序图01」，则文档中需出现该时序图或等价图，且逻辑一致。
- **图中要素**：参与方（用户角色、前端界面、后台服务、第三方系统）、关键消息/行为顺序、主要分支与异常返回，可选标注接口名或事件名，但仍以业务视角为主。

对于**简单功能**（如单表单、单页面列表、纯展示详情等），若业务流程清晰且文字已能完整表达，可不附流程/时序图。

### PlantUML 图表与自动渲染要求

- **流程与状态图表（PlantUML）**：若业务模块中涉及多角色协同（泳道图）、复杂状态流转（状态机图）、系统间交互顺序（时序图）或复杂判断条件（流程图），必须使用 **PlantUML 代码语法** 绘制相应的可视化图表，并在模块对应的功能说明位置**嵌入渲染后的图片**，而非仅贴源码。
- **自动图片生成**：使用本 skill 生成或更新 PRD 时，应将文中 PlantUML 代码自动转换为 PNG 图片，保存在当前 PRD 文件所在目录下的 `plantuml-images/` 文件夹中；图片按需覆盖更新，无需保留历史版本。
- **图片管理**：
  - 所有 PlantUML 生成的图片统一存储在 PRD 同级目录下的 `plantuml-images/` 文件夹中；
  - 当 PRD 文件中的 PlantUML 代码发生变更，重新执行本 skill 时自动重新生成并覆盖对应图片；
  - 图片按照在文中出现的顺序命名为 `diagram1.png`、`diagram2.png` 等，并在对应图表位置以 Markdown 图片形式嵌入。

## 全场景微交互与元素约束标准

在「页面结构与交互」「业务逻辑与状态流转」「异常与边界」中，按元素类型**强制应用**以下规范。

### A. 文本与数据展示规范

- **静态与动态**：静态文案用双引号明确；动态文案明确数据来源及拼接规则。
- **溢出与截断**：超长时的处理（单行截断加「...」、最大字数截断、换行、走马灯等）。
- **空态/兜底**：无数据时的占位（如「-」「暂无内容」）。

### B. 按钮/操作类（生命周期六步法）

必须明确：1. 初始化条件 → 2. 默认态 → 3. 触发指令（单击/长按等）→ 4. 执行中过程态（防抖/加载动画）→ 5. 执行异常（提示与重试）→ 6. 执行成功（跳转/刷新/状态变更）。

### C. 表单/输入框

- 键盘与聚焦：是否自动聚焦、唤起何种键盘（数字/英文/限制标点）。
- 校验时机：实时/失焦/提交时校验。
- 边界约束：字数上下限、极值、非法字符过滤及对应错误轻提示文案。

### D. 列表与加载

- 加载方式：分页、上拉无限滚动或虚拟列表。
- 过程反馈：下拉刷新/上拉加载的视觉与文案（如「正在加载更多」）。
- 边界状态：首页无数据（空状态）、加载失败（重试）、到底（「已经到底啦」等）。

### E. 弹窗与系统级中断

- 遮罩是否可点关闭、多弹窗时的优先级（排队/覆盖）。
- 系统级中断（如全局告警、强权限任务）时当前弹窗的降级或关闭逻辑。

### F. 环境降级

- 无网、弱网、权限不足、传感器或外部服务不可用时的展示与引导策略；本地缓存与离线可读范围（若适用）。

### G. 页面操作点检查表（避免遗漏按钮/交互）

- 对于每个主要页面或复杂区块，应在「页面结构与交互」下增加一份**操作点检查表**（可用表格形式），至少包含：
  - 操作名称（按钮文案/图标含义/链接文案）；
  - 触发位置（在哪个区域/哪行数据/列表还是详情）；
  - 触发条件（何时可点、何时置灰/隐藏）；
  - 点击后结果（跳转/弹窗/抽屉/状态变更等）；
  - 涉及的关键校验或前置检查（如有）。
- 在评审 PRD 或对照原型时，应逐行核对操作点检查表，确保每个操作在原型与交互说明中都有对应的入口与结果，避免遗漏按钮行为。

## 微交互与边界（摘要速查）

- **按钮**：六步法（初始化→默认→触发→执行中→异常→成功）。
- **表单**：数据来源、校验时机、边界与错误文案；新建/编辑差异。
- **列表**：分页方式、加载中/空态/失败/到底。
- **弹窗**：遮罩、多弹窗优先级、系统级中断。
- **降级**：无网/弱网/权限/外部不可用。

## 附录与 UML 源码归档

- 每篇 PRD 文档末尾必须包含「附录」（Appendix）或等价章节，用于**集中归档本 PRD 中使用的所有 PlantUML 源码**。
- 附录中的每段 PlantUML 源码需要注明图表编号或名称（如「diagram1：告警处理时序图」），以便与正文中嵌入的图片一一对应。
- 后续如需维护或修改图表，应优先修改附录中的 PlantUML 源码，再由本 skill 自动重新渲染并更新 `plantuml-images/` 中的图片。

## 可选步骤：根据 PRD 生成/更新原型

当用户要求「根据 PRD 出可点击原型」或「写 PRD 并出原型」时：确认项目约定的文档根、PRD 根、原型目录与 README；读取目标 PRD 及所属 README 中的 UI/设计规范；在约定原型目录下用 HTML + Tailwind + Lucide + 原生 JS 增改页面/区块/抽屉；关键区块用 HTML 注释标 PRD 编号或功能名；更新该目录 README 的「与 PRD 对应关系」和「文件说明」。原型设计应遵循「能还原的尽量还原（应用尽有）」的原则：在不依赖后端的前提下，尽量还原页面布局、组件状态、主要交互流程与边界状态；若项目中已安装或约定 UI/UX 规范（如 ui-ux-pro-max skill 中的设计原则），应尽可能按该规范执行。完整约定见项目内标准参考文档。

## 与其它 Skill 的配合

- **标准参考文档**：文档根、八段式、索引表、原型约定以项目内 product-doc-standard/README.md（或等价文件）为准。
- **product-featurelist**：PRD Header 的「对应 FeatureList 编号」来自功能清单的编号列；**单篇 PRD 仅对应一条或索引表/README 中界定的一小组编号**，新增 PRD 时索引表与 Feature List 一致，且须维护「编号 ↔ PRD 文件」对照。
- 微交互与撰写细节以本 skill 内「全场景微交互与元素约束标准」「新建/编辑页与字段规格」「时序图与流程图表」等节为准；文档存放、八段式、编号引用不依赖外部链接。

## 使用方式与执行顺序（必须遵守）

执行本 skill 时须按以下规则与顺序操作，与「文档结构」「写作铁律」中的按编号拆分、禁止合并一致：

1. **先列编号与模块映射**：根据 Feature List 列出所有待写 PRD 的 FeatureList 编号及其所属模块；决定每个编号对应哪一篇 PRD 文件（一个编号一篇，或明确的一小组一篇），再落盘，确保**文件按编号拆、目录按模块分**。
2. **按编号粒度调用**：一次只针对**一条**或**一小群紧密相关的** FeatureList 编号生成/完善对应的**单篇** PRD；不得为「整个模块」或「减少文档数」产出「一篇挂多编号」的 PRD。
3. **模块目录 + 单功能 PRD 文件**：按模块建目录（如 `prd/backend/M2_飞书同步/`、`prd/frontend/F3_校招信息表/`），在每个目录下以「编号+功能名」保存单篇 PRD（如 `M2.2_飞书同步任务_PRD.md`、`F3.1_校招页概览与24h统计_PRD.md`）；该目录的 README 或项目 PRD 索引表须维护「FeatureList 编号 ↔ 功能简述 ↔ PRD 文件」对照表。
4. **拆到最小 story**：当一条 FeatureList 包含多个相对独立的业务 story 时，应优先在 FeatureList 中拆分编号，再**分别**为每个编号生成各自 PRD 文件，不得在一个 PRD 中挂多个编号。
5. **迭代过程**：在已有模块下新增功能时，为新编号单独创建新的 `_PRD.md` 文件；仅在索引表/README 中已明确界定为「一小组」时，才可在同一 PRD 内覆盖多条编号，避免 PRD 越写越大、难以维护。

### 示例 1：登录页「获取验证码」按钮

**用途**：演示如何为一个简单控件（按钮）撰写完整的交互与状态流转说明，包含生命周期六步法与异常/边界场景。

#### 3.1 获取验证码按钮

- **位置**：登录表单内，验证码输入框的右侧。
- **目标**：下发短信验证码并防止恶意刷短信。

##### 3.1.1 界面元素与展示规则

- 静态文案：默认显示「获取验证码」。
- 动态文案：倒计时状态下显示为「{N}s 后重发」，其中 N 来自系统倒计时变量。
- 按钮宽度固定，长文案需自动缩小字号；不允许出现换行。

##### 3.1.2 交互逻辑与状态流转（按钮生命周期六步法）

1. **初始化条件**：手机号输入框内的内容通过 11 位手机号正则校验。
2. **默认态**：
   - 当手机号非法时，按钮为置灰不可点击态；
   - 当手机号合法时，按钮为高亮可点击态。
3. **触发指令**：用户单击按钮。
4. **执行中过程态**：
   - 按钮内部展示旋转加载动画；
   - 按钮进入禁用态，开启 1 秒防抖，防止重复点击。
5. **执行异常**：
   - 网络异常或服务端返回错误时，停止加载动画，恢复高亮可点击态；
   - 顶部弹出红色轻提示「发送失败，请检查网络后重试」；如命中风控，提示「当前请求存在安全风险，请稍后再试」。
6. **执行成功**：
   - 进入 60 秒倒计时，按钮置灰不可点，文案实时更新为「{N}s 后重发」；
   - 倒计时结束后自动恢复为高亮「重新获取」状态。

##### 3.1.3 异常与系统边界

- 弱网场景：若 8 秒内未收到响应，视为超时失败，进入执行异常流程。
- 应用切后台：倒计时期间若用户切到后台并重新回到前台，按钮应根据本地时间自动校准剩余秒数，不允许倒计时暂停或重置。

### 示例 2：B 端活动证书查询与异步导出

**用途**：演示列表+筛选+异步导出功能的写法，强调字段展示、隐私脱敏、异步导出闭环。

#### 1. 项目背景

- **需求简介**：构建标准化证书查询列表，支持多维度检索，并提供大文件异步导出功能，提升管理员处理大批量数据的效率。
- **业务诉求**：解决原有同步导出机制在面对万级数据时容易超时卡死的问题，实现数据导出的异步闭环。

#### 2. 业务流程简述

管理员进入证书列表 → 组合筛选目标考生 → 触发异步导出指令 → 系统后台生成文件 → 管理员在消息中心获取反馈并下载文件。

#### 3. 详细功能需求说明

##### 3.1 学生证书管理列表

- **位置**：管理后台侧边栏 →「学生证书管理」。
- **目标**：提供以「考生」为维度的全局证书查询入口，并进行个例化的管理操作。

###### 3.1.1 筛选查询区（数据输入与校验约束）

1. **学生姓名输入框**：
   - 静态文案：占位符显示「请输入学生姓名」。
   - 交互规则：支持模糊搜索。按下回车键或点击「查询」按钮触发检索。
   - 边界校验：限制最多输入 20 个字符，超出无法继续输入。
2. **身份证号输入框**：
   - 静态文案：占位符显示「支持后 6 位检索」。
   - 交互规则：支持精确匹配。
   - 边界校验：
     - 仅允许输入数字和字母「X」，输入非法字符实时过滤；
     - 失去焦点时，若内容不为空且长度不等于 6 或 18 位，下方标红展示轻提示：「请输入正确的身份证号格式」。

###### 3.1.2 数据列表区（文本展示与空态约束）

1. **初始化与默认态**：
   - 列表默认按「生成时间」倒序排列；
   - 每页默认展示 20 条数据，可切换分页。
   - 若查询结果为空，列表区域展示全局空状态插画，底部文案提示：「暂无符合条件的证书记录」。
2. **手机号/身份证号（隐私脱敏规则）**：
   - 手机号：保留前 3 后 4 位，中间 4 位用「*」代替（例：`138****8888`）；
   - 身份证号：仅展示前 3 位与后 2 位，中间全部用「*」代替（例：`110**********23`）。
3. **渠道信息（截断规则）**：
   - 动态文案：合并显示「渠道名称」与「渠道编号」；
   - 溢出处理：限制最大宽度 150px。超出部分单行截断，尾部展示「...」，鼠标悬停 (Hover) 时通过文字气泡展示完整内容。

###### 3.1.3 证书状态指示器（状态机映射表格）

列表右侧的「证书状态」字段，需根据后台实际处理进度，严格按照下表进行视觉与状态映射：

| 后台证书状态 | 前端显示文案   | 图标 (Icon) | 视觉风格 (Color) |
| :----------- | :------------- | :---------- | :---------------- |
| 批改中       | 「批改中」     | 旋转加载圈  | 橙色（警告色）    |
| 待复核       | 「证书复核中」 | 双对勾      | 蓝色（常规色）    |
| 制作中       | 「证书制作中」 | 打印机      | 靛青色（主色调）  |
| 已寄送       | 「证书已寄送」 | 运输包裹    | 绿色（成功色）    |

###### 3.1.4 异步导出操作（全生命周期交互闭环）

「导出数据」按钮及关联流程，严格遵循以下生命周期：

1. **默认态**：
   - 位置：列表右上角常驻显示「导出数据」按钮，使用蓝色实心主按钮样式。
2. **触发指令**：
   - 用户左键单击按钮。
3. **前置校验**：
   - 若当前列表无数据（总条数为 0），阻断执行；
   - 页面顶部弹出轻提示：「当前无数据可导出」，按钮保持默认态。
4. **执行中（过程态）**：
   - 按钮文案立即变更为「正在导出...」，并在文案左侧增加转圈加载动画；
   - 按钮进入禁用状态（不可再次点击，防止重复提交）；
   - 页面顶部弹出全局提示框（停留约 3 秒后自动消失）：「正在导出，请稍后在『消息中心』查看并下载」。
5. **执行成功（本页等待场景兜底）**：
   - 若用户未离开当前页面且导出在短时间内完成，按钮文案变更为「下载文件」，视觉样式变更为绿色高亮；
   - 用户点击即可直接通过浏览器下载文件。
6. **执行成功（离开页面场景兜底）**：
   - 若用户在生成期间刷新页面或跳转至其他菜单，再次返回本页时，按钮恢复为默认态；
   - 用户需前往独立的「消息中心」页面查看历史记录并下载。

### 示例 3：教师端编程 OJ 题录入与试卷赋分

**用途**：演示动态表单、字段联动与批量赋分规则的写法。

#### 1. 项目背景

- **需求简介**：在教师端题库中新增「编程 OJ」题型的录入与测试用例配置能力，并支持试卷级别的统一动态赋分与绝对分值评价映射。
- **业务诉求**：满足教研团队对在线代码题（支持 Scratch3、Python 等）的自动化判分需求，并解决非百分制试卷无法准确映射 A–F 评级的问题。

#### 2. 业务流程简述

教师进入题目详情 → 录入题目描述 → 唤起测试用例配置弹窗 → 根据题型选择检查逻辑（运行比对或正则匹配）→ 保存配置 → 在试卷模块进行批量赋分。

#### 3. 详细功能需求说明

##### 3.1 编程 OJ 测试用例编辑弹窗

- **位置**：题目详情页 → 评分标准模块 → 点击「添加测试用例」按钮。
- **目标**：规范化录入自动判分的输入/输出标准或正则规则。

###### 3.1.1 界面元素与数据校验规范（动态表单）

弹窗标题为「测试用例」，包含以下通用字段与联动字段：

1. **用例名称（文本输入）**：
   - 状态：必填项。
2. **权重值（数字输入）**：
   - 状态：必填项；
   - 校验：必须为正整数。失焦时若非正整数，清空输入框并展示轻提示：「权重值请填写正整数」。
3. **得分占比（纯文本展示）**：
   - 状态：不可编辑；
   - 动态计算规则：实时显示当前用例权重值占「所有用例权重值总和」的百分比（向下取整显示整数百分比）。
4. **用例类型（单选组件）**：
   - 状态：必选项。包含两项：「用例检查」「正则匹配」。
   - 联动逻辑 A：选择「用例检查」时，下方展示「运行输入」（多行文本，必填）与「运行输出」（多行文本，必填）。
   - 联动逻辑 B：选择「正则匹配」时，下方展示：
     - 「正则表达式」（文本框，必填）；
     - 「包含」（多行文本，可选）；
     - 「不包含」（多行文本，可选）；
     - 「匹配方式」（单选：查找/全匹配，必选）。
   - 约束：当选择「正则匹配」时，「正则表达式」「包含」「不包含」三者至少填写一项，否则视为校验不通过。

###### 3.1.2 交互逻辑与状态流转（弹窗生命周期）

1. **取消/关闭弹窗**：
   - 触发指令：点击底部「取消」按钮或右上角「×」；
   - 结果：不保存任何修改，直接销毁弹窗。
2. **保存配置**：
   - 触发指令：点击底部「保存」按钮；
   - 异常态（校验阻断）：若必填项为空，或「正则匹配」下三选一条件未满足，阻断提交流程。弹窗不关闭，在弹窗内展示轻提示：「请检查必填字段按要求填写」；
   - 成功态：校验通过后，保存该条用例数据，关闭当前弹窗，并局部刷新底层用例列表。

##### 3.2 试卷批量赋分模块

- **位置**：试卷详情页 → 各题型模块标题栏右侧 → 点击「批量赋分」按钮。
- **目标**：快速统一修改某一题型下所有题目的分值。

###### 3.2.1 赋分弹窗与计算规则

1. **界面文案（动态拼接）**：
   - 弹窗内展示提示文案：「[A] 共计 [B] 道题，每道题满分为 [X] 分，共计 [Y] 分」；
   - 变量定义：
     - [A]：当前模块的标题名称（只读）；
     - [B]：该模块包含的题目总数（只读）；
     - [X]：输入框，供教师录入，必须校验为正整数；
     - [Y]：动态计算文本，公式为 `B * X`，教师修改 X 时实时更新。
2. **交互流转**：
   - 点击「确定」按钮后关闭弹窗；
   - 系统将该模块下所有题目的分值覆盖为 X，并重新计算试卷总分。

##### 3.3 全局评价映射策略（后台逻辑视角的业务规则）

- **目标**：解绑绝对百分制，使等级评价（A–F）适应任意总分的试卷。
- **动态映射规则**：假设试卷最终动态总分为 `X` 分，学生得分对应的等级阈值自动计算如下（四舍五入保留一位小数）：
  - A 等：得分 ≥ X × 90%；
  - B 等：得分在 [X × 80%, X × 90%) 区间；
  - C 等：得分在 [X × 70%, X × 80%) 区间；
  - D 等：得分在 [X × 60%, X × 70%) 区间；
  - E 等：得分在 [X × 45%, X × 60%) 区间；
  - F 等：得分 < X × 45%。

### 示例 4：OTA 云平台 - 车辆数字资产管理

**用途**：演示 B 端编辑表单 + 详情比对页的写法，强调只读字段、级联选择与比对展示规则。

3. **执行异常（校验阻断）**：
   - 若服务端校验失败（例如该 VIN 码已被其他车辆占用），阻断提交流程，停留在当前表单页；
   - 在表单顶部展示红色错误警示信息，如「该 VIN 已被其他车辆使用」。
4. **执行成功**：
   - 保存成功后，页面跳转回车辆列表页；
   - 在全局顶部弹出绿色轻提示：「车辆信息保存成功」。

##### 3.2 车辆详情监控页

- **位置**：车辆管理列表 → 列表中点击「查看车辆详情」进入。
- **目标**：聚合展示单一车辆的所有车端实际上报信息，并提供远程操作入口。

###### 3.2.1 ECU 配置比对渲染逻辑

在「ECU 信息」标签页中，需要将「标准配置要求」与「车端实际上报数据」合并为同一张表格展示。对于零件号、硬件号、硬件版本等核心参数单元格，执行以下比对渲染规则：

- **状态 A（数据完全一致）**：系统要求与实际上报完全相符，单行文本正常展示（默认颜色）。
- **状态 B（数据存在冲突）**：
  - 单元格内分两行展示：
    - 行 1：「云端：{系统要求值}」；
    - 行 2：「车端：{实际上报值}」，文本使用红色高亮警示。
- **状态 C（仅系统有配置数据）**：
  - 展示系统数据，并在后方拼接灰色备注文案：「（车端无数据）」。
- **状态 D（仅车端上报了未知数据）**：
  - 展示车端实际上报数据，并在后方拼接灰色备注文案：「（云端无数据）」。
- **状态 E（两端均无数据）**：
  - 展示灰色占位文案：「无数据」。

###### 3.2.2 远程控制指令下发交互（全生命周期）

在「远程控制」标签页内，用于向车端下发强制重启、日志上传等指令。

1. **默认态**：
   - 操作卡片内「选择操作」下拉框默认文案「请选择一个操作」；
   - 「推送」按钮为不可点击状态。
2. **触发指令**：
   - 用户在下拉框中选中某个操作（如「车辆锁止」）后，「推送」按钮高亮可点；
   - 点击「推送」按钮触发下发动作。
3. **执行中（过程态）**：
   - 「推送」按钮进入加载中状态（旋转图标或文字变化），禁止重复点击；
4. **执行结果展示**：
   - 下发动作完成后，下方「历史记录」列表在顶部新增一条记录；
   - 记录中的「状态」列根据车端真实物理响应动态流转为「已发送」「成功」「超时」或「失败」；
   - 若出现「超时」或「失败」，应在记录中展示简要原因（如「车端长时间未响应」「网络异常」）。
