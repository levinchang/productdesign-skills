# 产品文档结构规范（标准参考）

本文件为**与编辑器无关**的产品与研发文档结构标准，可直接复制到任意项目中使用（任意 IDE、协作平台、非 Cursor 环境均适用）。建立 FeatureList↔PRD↔ER↔时序图↔技术文档↔原型的追溯链，统一 PRD 八段式与索引表约定。

**使用方式**：将本文件或所在目录 `product-doc-standard/` 复制到项目文档根或 `docs/` 下，按需调整路径与命名后执行即可。在 Cursor 中若启用 product-featurelist / product-prd，会优先读取项目内本标准文档。

---

## 1. 文档根与两区划分

- **文档根目录**：由项目自定（仓库根、`docs/`、`designdocx/`、`product/` 等）。以下称「文档根」。
- **两区**：建议在文档根下区分「设计资产」与「PRD」：
  - **设计资产**：Feature List、ER 图、时序图、技术设计总览、技术文档目录（tech/）等，与 PRD 同级便于引用。
  - **PRD 区**：所有 PRD 按模块或按产品线/端组织；具体目录名与层级由项目约定。

**示例（仅作参考，非强制）**：

```
<文档根>/
├── README.md                     # 总览、文档类型与 PRD 关系表
├── <FeatureList 文件>.md         # 功能清单，命名由项目定
├── <ER 图>.mmd / <ER 说明>.md    # 数据模型，命名由项目定
├── 时序图01_<流程名>.mmd         # 时序图，命名由项目定
├── TECH_DESIGN_OVERVIEW.md       # 可选
├── tech/                         # 可选，技术设计文档
│   ├── README.md
│   └── 01_xxx.md, 02_xxx.md ...
└── prd/                          # PRD 根目录名可由项目改为 backend、frontend、modules 等
    ├── README.md                 # PRD 撰写规范、目录约定、索引表（见下）
    ├── prototype/                 # 可选，原型可放在 prd 下或各子域下
    │   ├── README.md
    │   └── *.html
    └── <模块目录>/                # 如 M1_登录、F1_账户、module_a 等，由项目定
        └── <功能>_PRD.md
```

**通用约定**：Feature List、ER、时序图、技术文档与 PRD 根同级或处于文档根下明确位置；模块目录与文件命名、编号体系由项目统一约定，并在 README 索引表中体现。

---

## 2. 文档追溯链

| 文档类型 | 约定 | 与 PRD 关系 |
|----------|------|-------------|
| Feature List | 文档根下，文件名由项目定 | 每篇 PRD **开头**必须注明「对应 FeatureList 编号」 |
| ER 图 | 文档根下，文件名由项目定 | PRD 中字段键名、校验与 ER 实体一致；技术文档与 ER 对齐 |
| 时序图 | 文档根下，编号+流程名 | PRD 中流程逻辑可引用对应时序图编号 |
| 技术文档(tech/) | 文档根下 tech/ 或等价目录 | 开发实现依据；与 PRD、ER 一致 |
| PRD | 按模块/产品线分目录 | 通过「PRD 索引表」由 FeatureList 编号反查 PRD 文件路径 |

**PRD 单文档 Header（必填）**：每篇 PRD 正文最前，用表格或列表注明「功能名称」「对应 FeatureList 编号」「对应 ER 实体」「对应时序图（如有）」。

---

## 3. PRD 目录与命名（项目可定制）

- 按模块或产品线建目录，名称与业务一致；是否区分前后台、用 M/F 等前缀由项目定。
- 每功能单文件；**文件名建议与文档内一级标题一致**。命名格式由项目统一（如 `M1.1_功能名_PRD.md`、`1.1_功能名.md` 等）。
- 同目录下逻辑说明、规则说明等，命名清晰即可。

---

## 4. PRD 单文档结构（八段式模板，通用）

每篇 PRD **必须**按以下顺序书写，缺一不可：

| 序号 | 章节 | 内容要点 |
|------|------|----------|
| 0 | **Header** | 功能名、FeatureList 编号、ER 实体、时序图（见 §2） |
| 1 | **需求背景与目标** | 为何做、做什么、期望效果；可含用户故事、验收标准 AC |
| 2 | **角色与入口** | 谁、从哪进、数据范围 |
| 3 | **页面结构与交互** | 布局、区块、操作、状态 |
| 4 | **字段规格表** | 必填/长度/格式/取值来源/校验/错误提示；键名与 ER 一致 |
| 5 | **业务逻辑与状态流转** | 规则、状态机、流程；可引用时序图 |
| 6 | **异常与边界** | 加载中、失败、空态、权限、网络等 |
| 7 | **依赖与待定项** | 依赖接口/模块；待产品与后端约定的项 |

---

## 5. 索引表约定（通用）

- **PRD 根目录的 README**：说明与 FeatureList 的对应关系、PRD 单文档结构、目录与命名约定；**必须包含「FeatureList 编号 ↔ 功能简述 ↔ PRD 文件路径」对照表**。若 PRD 按多子域拆分，可在各子域 README 维护各自索引表，或汇总在 PRD 根 README。
- 新增或重命名 PRD 时，必须同步更新对应索引表。
- 可选：在 README 中补充 UI/设计规范、模块与菜单/页面映射。

---

## 6. 原型目录与规范（通用）

- **位置**：由项目约定。常见为 PRD 根下 `prototype/` 或各产品线/端下分别 `prototype/`。
- **技术栈**：HTML + Tailwind CSS（CDN）+ Lucide Icons（或等价）+ 原生 JS，无后端、无构建。
- **每个原型目录必须有 README.md**：与 PRD 对应关系、设计规范摘要、文件说明、使用方式。HTML 关键区块用注释标注 PRD 编号或功能名（如 `<!-- [1.1] 登录弹窗 -->`）。

---

## 7. 根据 PRD 生成或更新原型（可选）

执行时：确认项目约定的文档根、PRD 根、原型目录与 README；读取目标 PRD 及所属 README 中的设计/UI 规范；在约定原型目录下新增或修改 HTML，并更新该目录 README 的「与 PRD 对应关系」和「文件说明」。原型以占位、弹窗、抽屉、页面切换为主，不接真实后端。

---

## 8. 技术设计文档（tech/，可选）

文档根下 `tech/` 或项目约定等价目录。tech/README 列出各技术文档及与 ER、时序图、Feature List/PRD 的对应关系；各 .md 按主题拆分，引用 ER、时序图及 PRD，不重复需求描述。可选 TECH_DESIGN_OVERVIEW.md 作总览索引。

---

## 9. 检查清单（创建或修改文档时自检）

- [ ] 新 PRD 在项目约定的模块/产品线目录下，文件名与文档内标题一致（或符合项目命名规范）。
- [ ] PRD 开头已填 Header（功能名、FeatureList 编号、ER 实体、时序图）。
- [ ] PRD 具备八段：Header、需求背景与目标、角色与入口、页面与交互、字段规格、业务逻辑与状态流转、异常与边界、依赖与待定项。
- [ ] 项目约定的 PRD 索引表（README）已更新。
- [ ] 若涉及原型：原型目录 README 中「与 PRD 对应关系」已更新；HTML 关键处已标 PRD 编号或功能名。
- [ ] 字段键名、枚举与 ER 图一致；流程描述引用的时序图编号正确。
