# 产品功能清单（Feature List）

将业务需求拆解为结构清晰、MECE 的 Feature List，供 PRD 与原型逐条设计使用。**表头必须**采用本标准（见下）；**输出位置与编号体系**以项目内标准参考文档为准。

---

## 何时使用

- 用户要求把业务需求、流程图或想法拆解为功能清单时。
- 版本规划阶段，需要明确本轮先做哪些 Story 时。
- 需要为已有产品补充或修订 Feature List，并与 PRD、原型保持追溯关系时。

---

## 表头定义（必须遵循）

输出的 Feature List **必须**包含以下列，顺序与列名不可擅自增删改。

| 列名 | 说明 |
|------|------|
| **Mark** | 状态标记，如 DONE、READY、REVIEW |
| **编号** | 功能编号，采用 `端-领域-模块序号.Story序号`，如 `WB-DM-1.1` |
| **领域（Domain）** | 业务域，如设备管理、告警、平台配置 |
| **一级（菜单/模块）** | 一级导航/模块 |
| **二级（菜单/页面）** | 页面级入口 |
| **功能（页内能力）** | 页面内具体能力块 |
| **子功能（可选）** | 对能力的进一步拆解 |
| **描述** | 做什么、解决什么问题 |
| **负责产品** | 负责人 |
| **必要性** | Must/Should/Nice to 或 P0/P1/P2 |
| **涉及端** | Web 管理端、小程序、App、触摸屏等 |
| **期望版本** | 目标发布版本 |
| **优先级** | 业务优先顺序（如 H/M/L 或 1/2/3） |
| **状态** | `TODO` / `READY` / `IN_DESIGN` / `IN_PRD` / `DONE` |
| **依赖** | 依赖的编号清单，可为空 |
| **计划迭代** | 目标迭代，如 `V2.3-S1` |
| **Ready** | 是否满足进入设计条件（Yes/No） |
| **说明** | 补充说明或约束 |
| **备注** | 风险、待定项等 |

- 表格内容必须为纯文本，避免复杂嵌套与多行结构。
- 若项目已存在一致表头，优先沿用并增量更新。

---

## 双入口策略（不强制 Roadmap）

- **入口 A：用户指定先做项（默认优先）**
  - 若用户明确指定某个模块/编号，直接进入该项设计，不受其他条目阻挡。
- **入口 B：按优先级推进**
  - 若用户未指定，优先选择 `Ready=Yes` 且优先级最高、依赖已满足的条目。

这意味着 Feature List 既是功能清单，也是轻量计划面板，不需要额外的 roadmap skill。

---

## 层级与颗粒度约定

- 一条 Feature List 行 = 一个可单独评审、单独验收的 Story 单元。
- 禁止同一层级混用“整页能力”和“单按钮动作”。
- 默认一条编号对应一篇 PRD；仅在强耦合小组（2-4 条）且同闭环验收时允许合并。

---

## 输出位置与编号（项目约定）

- 文件路径由项目文档结构约定；未约定时默认放在 `docs/02_feature_list.md`。
- 编号结构固定：`<端前缀>-<领域前缀>-<模块序号>.<Story序号>`。
- 保持编号全局唯一，避免跨模块重名冲突。

---

## 工作流

1. 识别本次范围与候选 Story。
2. 补齐编号、优先级、状态、依赖、迭代与 Ready 字段。
3. 选择执行入口：
   - 用户指定编号：直接进入；
   - 未指定：按 Ready+优先级自动选择。
4. 一次只推进一个 Story（或一小组强耦合 Story）进入 PRD/原型阶段。
5. 完成后回填状态与说明，保持 `FeatureList -> PRD -> Prototype` 可追溯。

---

## 与 PRD / 原型的关系

- PRD Header 必须引用 FeatureList 编号。
- 原型变更必须能回溯到 FeatureList 编号与变更编号。
- 未进入 `Ready=Yes` 的条目，不建议直接进入高保真原型。

---

## 本地环境下默认落盘行为（Cursor / Codex）

1. 优先读取项目标准文档，确定 Feature List 路径。
2. 若无标准文档，则默认创建/更新 `docs/02_feature_list.md`。
3. 每次更新后在对话中反馈：改动条目、状态变化、当前进入设计的编号。
