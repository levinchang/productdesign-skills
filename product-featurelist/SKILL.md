# 产品功能清单（Feature List）

将业务需求拆解为结构清晰、MECE 的 Feature List，供 PRD 撰写与研发排期使用。**表头必须**采用本标准（见下）；**输出位置与编号体系**以项目内**标准参考文档**为准（见「项目内标准参考文档」节）。本技能不依赖 product-doc-structure skill。

---

## 何时使用

- 用户要求把业务需求、流程图或想法拆解为「功能清单（Feature List）」时。
- 产品立项或版本规划阶段，需要明确各系统模块及细分功能时。
- 需要为已有产品补充或修订 Feature List，并与现有 PRD 目录、索引表对齐时。

---

## 表头定义（必须遵循）

输出的 Feature List **必须**包含以下列，顺序与列名不可擅自增删改。可直接复用本 skill 目录下 [featurelist_template.md](featurelist_template.md) 的模板。

| 列名 | 说明 |
|------|------|
| **Mark** | 状态标记，如 DONE（已完成）、READY（就绪）、REVIEW（评审中）等，由项目约定取值 |
| **编号** | 功能编号，采用「端前缀-领域前缀-模块序号.Story序号」两级结构（如 `WB-DM-1.1`），便于与 PRD 对应、索引表反查；每一条编号都是一个可以单独评审/排期的 Story 单元 |
| **端（Client）** | 功能所在的端形态，如 Web 管理端、小程序、触摸屏、手机 App、PC 客户端、设备端等；仅填用户可见使用载体，不填「后端」「服务端」等技术层 |
| **领域（Domain）** | 业务域，如 设备管理、运维作业、监控与告警、知识与经验、备品备件、报表分析、平台配置 等 |
| **一级（菜单/模块）** | 端 + 领域 下的一级导航/模块，如（Web 后台）设备管理、运维作业、监控与告警、系统设置；通常对应左侧一级菜单或顶栏一级 Tab |
| **二级（菜单/页面）** | 一级模块下的二级菜单或主页面入口，如 设备台账、设备树、工单管理、知识库 等；通常对应路由/页面级入口，而非第三级菜单 |
| **功能（页内能力）** | 二级菜单/页面下的具体功能或能力块，如 设备列表展示、设备详情、点检计划制定、告警列表、知识条目管理 等 |
| **子功能（可选）** | 功能的进一步拆解，如 分页与排序、导入模板与校验、导出、关联告警与工单入口 等；仅在确有必要细拆 Story 时使用，可为空 |
| **描述** | 该功能点的详细说明或用户故事，说明「做什么、解决什么问题」 |
| **负责产品** | 负责该功能的产品经理或角色，由项目定（如 产品经理A、PM-前端） |
| **必要性** | 优先级/必要性，如 Must、Should、Nice to、Maybe 或 P0/P1/P2、V1/V1.1 等 |
| **涉及端** | 功能涉及的**用户可见使用载体**（如 Web 管理端、触摸屏、小程序、手机 App、PC 客户端、设备端）；仅填终端/端形态，不填「后端」「服务端」等技术层；如与「端（Client）」列含义重叠，可按项目约定选择保留其中一列或统一用一列表示 |
| **期望版本** | 目标发布版本（如 V1.0、V2.0、OTA） |
| **说明** | 补充说明、约束或与其它条目的关系 |
| **备注** | 其它备注（依赖、风险、待定等） |

- **表格内容**：纯文本，单元格内避免复杂嵌套列表或换行，以便复制到 Excel/飞书不乱码。
- 若项目已有 Feature List 且表头与本标准一致，**优先沿用**，仅补充或修订行内容；若项目表头与本标准不同，以项目约定为准，但建议新项目采用本标准表头。

## 层级与颗粒度约定

- **端（Client）**：功能在哪个端交付，用户通过什么载体使用，如 Web 管理端、小程序、触摸屏等。端只影响导航结构与原型/路由路径，不代表技术实现层（如后端服务）。
- **领域（Domain）**：业务域，如 设备管理、运维作业、监控与告警、知识与经验、备品备件、报表分析、平台配置 等。领域用于横向划分业务范围，不直接等同于菜单层级。
- **一级（菜单/模块）**：某一端 + 领域 下的一级导航/模块，如（Web 后台）设备管理、运维作业、监控与告警、系统设置；通常对应左侧一级菜单或顶栏一级 Tab。
- **二级（菜单/页面）**：一级模块下的二级菜单或主页面入口，如 设备台账、设备树、工单管理、知识库 等；通常对应路由/页面级入口，避免再出现第三层菜单心智。
- **功能（页内能力）**：二级菜单/页面下的具体功能或能力块（一个 Story 可以覆盖一个或多个控件/区域），是用户可感知的独立能力或数据展示单元。
- **子功能（可选）**：在功能粒度仍过大时，对其进行进一步拆解的 Story 单元，如「分页与排序」「导入模板与校验」「导出」「异常关联报修/工单」等；若无必要可留空。

同一层级下颗粒度保持一致，避免混用「整页」与「单按钮」同级；**一条 Feature List 行 = 一个可单独评审和排期的 Story 单元**，不要使用「父行+子行」混合承载 Story 的方式（例如同时让 1 和 1.1 都是 Story）。

## 描述、说明与备注

- **描述**：建议采用用户价值或规则说明，如「按设备类型、状态筛选并分页展示设备列表」「为设备指标配置阈值，超限触发告警」；或采用 `As a [角色], I want to [动作], so that [业务价值]`。
- **说明**：补充说明、约束、与其它条目的关系。
- **备注**：前置系统依赖、软硬件/外部 API 依赖、与其它 Feature 的先后依赖、风险与待定项。

## 输出位置与编号（项目约定）

- **文件路径**：由项目文档结构约定。通常为**文档根目录**下的单文件，或按产品线/端分文件。先确认当前项目文档根与命名习惯再落盘。
- **编号体系（强制规则）**：
  - 采用统一的「端 + 领域 + 模块序号.Story 序号」结构：`<端前缀>-<领域前缀>-<模块序号>.<Story序号>`，例如：
    - `WB-DM-1.1`：Web 管理端（WB）+ 设备管理领域（DM）+ 模块 1（如设备台账）+ Story 1（如「设备列表展示（分页/排序/搜索/筛选）」）。
    - `MP-OPS-1.3`：小程序端（MP）+ 运维作业领域（OPS）+ 模块 1（如点检保养）+ Story 3（如「任务执行与填报」）。
  - **端前缀**：根据「端（Client）」列自动映射，建议在项目内标准文档中统一约定，例如：Web 管理端→`WB`，小程序→`MP`，触摸屏→`TS`，手机 App→`APP`，PC 客户端→`PC` 等。
  - **领域前缀**：根据「领域（Domain）」列自动映射，例如：设备管理→`DM`，运维作业→`OPS`，监控与告警→`MON`，知识与经验→`KB`，备品备件→`SP`，报表分析→`RPT`，平台配置→`CFG` 等；可在项目标准文档中扩展。
  - **模块序号**：同一「端 + 领域」下，按一级（菜单/模块）的顺序从 1 开始编号（1、2、3…），该数字**不单独作为一行 Story 出现**，仅用于构成编号和目录命名。
  - **Story 序号**：同一模块内，按行顺序从 1 开始编号（1、2、3…），每一行 Feature = 一个 Story；不存在「父编号也是 Story，子编号也是 Story」的情况。
  - 在同一项目内，**一条编号全局唯一**，避免出现因不同端/模块重名导致的编号冲突。
- **与 PRD/原型的对应关系**：
  - 每个 PRD 的 Header「对应 FeatureList 编号」须使用上述完整编号（如 `WB-DM-1.1`），并与 Feature List 一致。
  - PRD 目录推荐采用「端 + 模块编号」命名，例如：`docs/prd/backend/1_设备管理/1.1_设备台账_设备列表展示_PRD.md`；其中 `1` 来源于「端=WB、领域=DM」下的模块序号，`1.1` 对应 Story 序号。
  - 原型目录推荐按「端 + 一级菜单」拆分，编号主要用于在 README 或索引表中建立「编号 ↔ 页面/路由」的对照关系，而不是强行塞入所有文件夹名中。
- **同步**：新增或修改功能后，更新项目约定的 PRD 索引表，保证按编号可反查 PRD 路径；索引表中须包含「FeatureList 编号 ↔ PRD 文件 ↔ 原型路径」的对照。

## 工作流

1. **理解需求**：阅读用户提供的背景、目标、已有 PRD 或流程图，识别领域与模块边界。
2. **确认项目约定**：当前项目的文档根、Feature List 文件命名与位置、编号体系（若已有 PRD 或索引表，与之对齐）。
3. **确定编号策略**：与现有 Feature List 或 PRD 目录一致；如项目未约定，则在对话中与用户确认一套简单可维护的编号规则。
4. **输出表格**：按**表头定义**输出 Markdown 表格，填写 Mark、编号、〇级～四级、描述、负责产品、必要性、涉及端、期望版本、说明、备注。
5. **落盘与同步**：在本地可写环境中，写入项目约定的 Feature List 路径；若有新增或变更，更新项目约定的 PRD 索引表；在纯对话/云端环境中，仅输出 Markdown 表格与「推荐存放路径」说明，不直接创建文件。

## 本地环境下的默认落盘行为（Cursor / Codex）

- 在本地可写文件的环境中，使用本 skill 时应遵循以下默认行为：
  1. **优先读取项目标准文档**：按「项目内标准参考文档」一节的优先级查找并读取标准文档，获取文档根（如 `docs/`）、Feature List 路径、编号体系等约定。
  2. **若无标准文档则创建最小模板**：当项目中未发现任何标准文档时，应在仓库根创建 `product-doc-standard/README.md`，可参考本 skill 同目录下 `product-doc-standard/README.md` 作为最小默认模板，并在其中约定：
     - 文档根目录：默认为 `docs/`；
     - Feature List 默认路径：默认为 `docs/02_featurelist.md`；
     - 后续可由项目成员按需修改。
  3. **保证 Feature List 文件存在**：根据标准文档中的约定路径（或默认路径）创建或更新 Feature List 文件；若文件不存在则新建。
  4. **显式反馈文件变更**：在对话中简要列出本次新建或更新的文件路径，便于用户在编辑器中打开查看。

## 0-1 与 1-n 场景的使用方式

- **0-1 场景（新产品/新子系统）**：
  - 结合产品蓝图或用户提供的背景信息，先识别领域（〇级）与模块（一级），生成能力（二级）骨架；
  - 在骨架基础上，由本 skill 提出初步的功能（三级）与子功能（四级）建议，用户按需删减或补充；
  - 为每一行补齐必要性、期望版本、涉及端等字段，形成该产品/子系统的首版 Feature List。
- **1-n 场景（版本迭代/模块增强）**：
  - 读取已有 Feature List 与标准文档，结合用户描述的「本次版本目标/范围」筛出相关领域与模块；
  - 根据用户意图选择：
    - 在**现有 Feature List 文件上增量更新**（新增/修改/下线部分行）；或
    - 基于某一版 Feature List **派生出新版本文件**（如新大版本）；或
    - 为新增的产品线/子系统 **单独新建一份 Feature List 文件**；
  - 保持编号体系与项目约定一致，如需要调整编号规则，应与用户确认后再执行。

## 项目内标准参考文档（优先遵循）

文档根、Feature List 路径、编号体系、索引表约定等，以**项目中的标准参考文档**为准。执行时应按以下优先级查找并读取（若存在则遵循其约定）：

1. 当前项目内的 `.cursor/skills/product-featurelist/product-doc-standard/README.md`（本 skill 附带的标准结构说明，适合你现在这个仓库的场景）。
2. 项目文档根或 `docs/` 等目录下的 `product-doc-standard/README.md`。
3. 其他等价命名的标准文档：`docs/PRODUCT_DOC_STRUCTURE.md`、`docs/产品文档结构规范.md`、文档根下 `PRODUCT_DOC_STRUCTURE.md`。

若上述文件均不存在，则按本 skill 内通用约定执行。标准参考文档与编辑器无关，可在非 Cursor 环境中使用。

- Feature List 文件通常放在文档根（或标准文档中约定的位置），与 ER 图、时序图、PRD 根同级。
- 每个 PRD 的 **Header** 必须注明「对应 FeatureList 编号」；该编号来自本表格「编号」列。
- PRD 索引表中的「FeatureList 编号」与本文档编号一致，便于开发按编号反查 PRD 路径。
